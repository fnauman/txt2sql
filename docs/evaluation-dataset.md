# Evaluation Dataset And Scoring

This repository evaluates against deterministic public demo datasets instead of
live private data. This is the canonical reference for the failure taxonomy, the
value-aware comparison spec, the multi-fixture oracle, the current baseline, and
known coverage limits.

| Asset | Path |
|---|---|
| Core public benchmark | `datasets/core-public.json` (9 cases) |
| Paraphrase public benchmark | `datasets/paraphrase-public.json` (9 cases) |
| Edge-case public benchmark | `datasets/edge-cases-public.json` (17 cases) |
| Oracle controls (wrong and correct SQL per case) | `datasets/controls/*.json` |
| Value-aware comparator | `compareResultsDetailed` / `compareResults` in `src/benchmark.js` |
| Multi-fixture oracle | `scoreAgainstGold` in `src/eval/oracle.js` |
| Evaluation fixtures (seed, v2, v3) | `src/eval/fixtures.js`, data in `src/eval/fixture-data.js` |
| Fixture seeding | `scripts/seed-fixtures.js` (`npm run seed-fixtures`) |
| Fixture drift check (re-hashes every row) | `checkFixtureContent` in `src/eval/fixture-seeder.js` |
| Dataset verifier | `scripts/verify-dataset.js` (`npm run verify-dataset`) |
| Benchmark | `scripts/evaluate.js` (`npm run benchmark`) |
| Edge-dataset generator | `scripts/build-edge-dataset.mjs` |
| Demo seed | `scripts/seed-public-db.js` (the `seed` fixture) |

The edge-case suite is `edge-cases-public.json` = the 9 reused `core_public_*`
cases plus 8 dedicated `edge_public_*` cases, regenerated by
`npm run build-edge-dataset`.

These datasets are synthetic regression fixtures, not a substitute for early user
feedback. In the original deployment, real users surfaced bilingual terms,
shorthand product names, and compact temporal phrases that a hand-authored
benchmark would not contain until the system was put in front of them. Treat
production/user feedback as the source of new cases, then distill public-safe
versions into these datasets. **Do not** add generated traces, private database
dumps, or customer/vendor-specific examples here.

## Failure taxonomy

Each dedicated edge case carries a `failure_class` tag naming the specific
weakness it targets. The 8 classes in `datasets/edge-cases-public.json`:

| `failure_class` | What it traps |
|---|---|
| `metric_column_confusion` | Picking the wrong amount column (gross vs net, header vs line) for a metric. |
| `grain_confusion` | Aggregating at document-header grain when the question is about line items, or vice versa. |
| `wrong_join_path` | Choosing a plausible-but-wrong join path between two tables. |
| `campaign_join_path` | Taking the correct multi-hop campaign path (sales line → product → campaign) instead of a wrong shortcut. |
| `wrong_date_column` | Filtering on the wrong date (e.g. posting date vs document date). |
| `stale_snapshot_field` | Reading an obsolete denormalized/snapshot column instead of the live source. |
| `master_data_resolution` | Resolving a fuzzy entity term ("sparkling water") to the right product(s). |
| `aggregation_shape` | Producing the wrong result shape — e.g. a long grouped rowset when the question asks for values pivoted into separate columns. |

Every gold query is **execution-verified on all three evaluation fixtures** (see
below), so a failing benchmark run is a model regression, not dataset rot (use
`verify-dataset` to keep that true after schema/data changes).

## The multi-fixture oracle

On the original seed alone (9 documents, 10 lines), many plausible-wrong queries
return exactly the gold answer: line `TotalAmount` equals `NetAmount` on every
line, header `NetPayableAmount` equals `NetAmount`, the posting month always
equals the document month, the one canceled document has no postings, and so
on. The audit measured that the old oracle caught only 50 of 108 hand-written
wrong queries (46.3%) on it. Following test-suite accuracy (Zhong et al. 2020,
*Semantic Evaluation for Text-to-SQL with Distilled Test Suites*), a prediction
now counts as correct only if it returns the gold answer on **every** fixture:

| Fixture | Database | Facts |
|---|---|---|
| `seed` (primary) | `demo_retail` | The original demo facts (also `npm run seed-demo`). The product loop runs here. |
| `v2` | `demo_retail_v2` | The audit's hand-designed fixture (mutation workstream v2 + v2b), ported to code: header and line metrics separated (NetPayable = Net + 12.50, BillTotal = Gross + 7.25, line TotalAmount = Net × 1.05), header-level discounts, canceled documents in range (one with postings), documents on month-boundary days posted in another month, multi-line documents, a NULL-ProductId fee line, a manual journal with NULL SalesDocumentId, 2025 documents in the same months, sub-cent amounts, ties, stale snapshots. Plus the v2c rows added after the PR review (`addV2cFacts`): a posted March 2025 document with Urban Refresh products and a sparkling SKU that no non-canceled March 2026 document sells; same-customer, same-amount twin documents in January, February and March 2026 (equal header, line and posting amounts); the inactive customer buying in January–March 2026, in March the discontinued product; a canceled February sale of a product with no other February/March sale; a February delivery fee; March category totals out of category-ID order; Harbor Kiosk ordering once in April. |
| `v3` | `demo_retail_v3` | ~250 documents generated by a seeded PRNG (mulberry32, seed `V3_PRNG_SEED = 20260331`) over January – March 2025 and November 2025 – May 2026: boundary-day dates, cancellations, NULLs, stale snapshots, a customer tie, 12 products selling in March 2026 so a top-10 `LIMIT` binds (with a clear gap at the cut-off), the inactive customer buying in January–March 2026 (with a delivery fee), the discontinued product selling in March, and one same-amount twin document per month in January–March 2026 (`addV3Twins`). |

**All fixtures share identical master data** (customers, products, brands,
categories, campaigns, locations, document types, ledger accounts, price
lists) and differ only in the fact tables (`SalesDocument`,
`SalesDocumentLine`, `AccountingPosting`). The model's prompt context
(master-data candidates, product names) is resolved on the primary fixture
only, so a fixture with different dimension rows would test a different
question than the one the model saw. The master data includes the v2
discriminators for every fixture, the demo seed included: an active customer
with no sales (Harbor Kiosk), a second "Summit Grocers", a second Beverages
brand (Clearspring Waters), a tag-only seltzer, a still-water decoy, a second
sparkling SKU, a Northstar product in Snacks, and a discontinued product
("Oat Cookies Tin", `IsActive = 0`, Urban Refresh campaign) that the seed
never sells. The semantic layer needed no change: "seltzer" is already a
"sparkling water" alias, and the decoys do not match any alias. (Consequence:
the seed's active-customer count is 7, not 5.)

`npm run seed-fixtures` (admin credentials) creates, bootstraps and seeds all
three databases from code — no fixture is copied from another — and records
`name`, `content_hash`, `generator_version` and `prng_seed` in a
`_fixture_meta` table in each. It is idempotent: a database whose rows already
hash to the generated content (and whose meta row records it) is left alone;
any other database, including one whose rows were edited after seeding, is
rewritten (`--force` rewrites it anyway). The SELECT-only query user reads
every fixture through its `demo\_retail%` grant. A unit test pins the content
hashes, so a generator change is visible.

**Drift is detected from the rows, not the meta row.** `checkFixtureContent`
re-hashes every seeded table (about 1.6k rows over the three fixtures; it takes
milliseconds) and reports `current`, `drifted` (the meta row claims the
generated content but the rows differ), `stale` (seeded by an older generator)
or `missing`, plus whether the master tables equal the shared `MASTER_DATA`. `verify-dataset` fails on any
fixture that is not `current` or whose master data differs; the benchmark
reports the status, warns on drifted facts and refuses to run when a fixture's
master data differs (the model would be scored on different dimension rows than
the ones its prompt context came from). Both always read the fixture databases
(`demo_retail`, `demo_retail_v2`, `demo_retail_v3`): `DB_NAME` is not used,
and they print a note when it names another database.

Oracle rules (`scoreAgainstGold`):

- **Gold variants**: the gold plus any `alternative_expected_sql`. A prediction
  must match **one** variant on every fixture (mixing readings across fixtures
  does not count).
- **One column mapping**: the comparator's gold-column → prediction-column
  assignment must be the same on every fixture. `findSharedAssignment`
  searches for one mapping valid on every fixture at once (candidate carriers
  intersected across fixtures, partial mappings pruned by their row tuples);
  no common mapping is `inconsistent_assignment`, and a search cut off by its
  step bound fails closed as `assignment_search_exhausted`, never a pass.
- **Gold runs with its own timeout** (`GOLD_STATEMENT_TIMEOUT_MS`, 30 s), cached
  per fixture, so a slow gold never looks like a model failure; a failing gold
  is `expected_sql_error`, never a model error.
- **The prediction runs as the read-only query user** through
  `executeReadOnlySql`, with the statement timeout and a row cap of (largest
  gold row count + 1).
- **Signal checks and disallowed columns are warnings**, never failures (see
  below).

### Pins and alternative gold

- `expected_row_counts: { seed, v2, v3 }` pins the gold row count per fixture
  (`npm run verify-dataset -- --write-pins` rewrites them). An external dataset
  may still carry the older single `expected_row_count`; it is read as the
  seed's pin.
- `alternative_expected_sql: [sql, ...]` lists other readings a case accepts,
  each explained in the case `notes`:
  - `core_public_005` / `core_public_009` (and their paraphrases): a top-N ledger
    ranking that leaves out accounts with a zero debit / credit total;
  - `edge_public_008`: listing every customer (LEFT JOIN from Customer) with
    0/0 where it had no January/February sales — one alternative per reading.
    The former second alternative ("every customer with any non-canceled
    document", the form one gpt-4o-mini run produced) is gone: its customer set
    depends on unrelated months, so it is neither reading; it is now a negative
    control, like "customers with any 2026 document".

### Statuses and warnings

The benchmark status depends on values only: `pass`, `result_mismatch`, or
`retrieval_miss` (no match and an expected table was not retrieved); a failed
product loop reports `llm_error`, `validation_error`, `execution_error`,
`infra_error` or `aborted` from its `errorStage`; a broken gold is
`expected_sql_error`. `low_signal_success` and `disallowed_column_used` are no
longer failure statuses. They are warning flags on a result:

- **Signal checks** (`signal_checks`) are resolved through the comparator's
  column assignment (gold column names mapped to the prediction's columns), and
  reported as `signal_warnings`. Keyed by gold alias, they used to turn a
  correct answer with a different alias into a failure, and the audit found they
  never caught anything the comparator missed. `verify-dataset` still requires
  every gold to pass its own signal checks (gold health).
- **Disallowed columns** (`disallowed_columns`) are a token-based lint over the
  shared MariaDB tokenizer: comments, string literals and output alias
  definitions (`AS alias` and the implicit `expr alias`, read the way the
  validator reads them) never count, nor does a bare alias name in
  `GROUP BY` / `HAVING` / `ORDER BY`; `Table.Column` entries resolve table
  aliases; a table name entry means the table is referenced. Findings are
  `disallowed_column_warnings`.

## Comparison spec (value-aware scoring)

The legacy comparator (`compareRows`) keys each row by its exact lowercased
column name, so a correct answer with a different aggregate alias
(`total_net_sales_amount` vs `total_net_amount`) or an extra projected column was
scored as a `result_mismatch`. That cosmetic brittleness dominated real failures.

`compareResultsDetailed(expected, actual, comparison)` (`src/benchmark.js`)
returns `{ match, assignment, reason }`: it matches the gold's compared columns
to the model's columns by **value** — any name, any position, extra predicted
columns ignored — and checks the row tuples agree (the Spider-style
execution-match idea, allowing extra predicted columns). `assignment` maps each
gold column to the prediction column that carries it; `reason` is `match` or
the first failed requirement (`row_count`, `missing_columns`, `values`,
`column_order`, `scalar_column`, `ranking`). `compareResults` is its boolean
view.

A case opts in via a `comparison` block. **All** public cases carry one, so
value-aware scoring is active across every committed case; a dataset/case
*without* a `comparison` block falls back to the legacy exact-row behavior so
external datasets and `compareRows` callers are unchanged.

```jsonc
comparison: {
  mode: 'scalar' | 'rowset' | 'ranked',  // default 'rowset'
  compare_columns: [..gold column names], // default: all gold columns
  value_columns:   [..gold column names], // ranked: the ranking metric(s); default: first truly numeric gold column
  order: 'desc' | 'asc',                  // ranked: default 'desc'
  decimals: number,                       // rounding precision, default 2 (matches gold ROUND(.., 2))
  tolerance: number,                      // absolute numeric tolerance; default 0
  column_order: [..gold column names],    // these keep their relative SELECT-list order in the prediction
  null_as_zero: [..gold column names]     // NULL counts as 0 in these columns, on both sides
}
```

- Numbers match by equality after rounding to `decimals`, or — when `tolerance`
  is set — by true absolute difference (`|gold − actual| <= tolerance`).
- **Dates**: a JS `Date` (mysql2 returns DATE/DATETIME columns as local-time
  Dates) and a date/datetime string normalize to one canonical value
  (`YYYY-MM-DD`, or the full timestamp when the time is not midnight), so a DATE
  column matches a `DATE_FORMAT`/`CAST` string. Dates never equal numbers.
- **scalar / rowset**: an order-blind bijection of compared row tuples must exist.
- **ranked**: that bijection must exist **and** the model's primary value column
  must be monotonic in `order` (catches "didn't sort / sorted wrong" while
  tolerating tie reordering by label). Ranked mode assumes `NULL` metrics sort
  last. The default ranking column is the first **truly numeric** gold column
  (JS numbers), never a numeric-looking code string such as `AccountCode '4000'`.
- **Name pinning**: when exactly one prediction column has a gold column's
  name (ignoring case and punctuation), only that column may carry that gold
  column, and it carries no other. Aliases stay free otherwise, but a column the
  model labeled like the gold must hold the gold's values: a wrong
  `total_net_amount` next to a correct `net_amount_excl_fees`, or a canceled-
  inclusive `document_count` next to a correct `non_canceled_document_count`,
  fails. "Named like" (used below) means the same name ignoring case and
  punctuation, or a longer name containing the gold name's words as a whole run
  (`posted_document_count` for `document_count`) that is not directly preceded
  by a negation (`non_canceled_count` is not `canceled_count`); word boundaries
  matter (`inactive_customer_count` is not `active_customer_count`).
- **column_order**: values alone cannot tell `jan_net_amount` from
  `feb_net_amount`. For the listed gold columns, a carrier named like its gold
  column identifies itself (a correctly labeled February-first pivot passes);
  the other carriers must keep the gold's relative SELECT-list order, and none
  may be named like a different listed column. Limit: carriers named unlike any
  listed column (`january`, `february`) are judged by position only, so a
  label-only swap of such names in the gold's positions still passes. Used by
  `edge_public_008`.
- **null_as_zero**: in the listed gold columns NULL counts as 0 on both sides,
  so a conditional `SUM(CASE WHEN … THEN NetAmount END)` without `ELSE 0`
  (NULL for a month without sales) matches a gold with 0. Used by
  `edge_public_008`.
- **Scalar rule**: when the gold is a single value (one row, one compared column)
  and the prediction has several columns, the column carrying the gold value
  must be the one named exactly like the gold column when there is one;
  otherwise the prediction's only column of the value's kind (the only numeric
  column for a number), or its only column named like the gold column. So
  `{product_count: 4, feb_product_count: 1}` fails for a gold of 1, and so do
  hedges with two like-named readings (`posted_document_count`,
  `dated_document_count`). Known false negative: a correct answer plus one more
  numeric column under an unrelated alias (`{urban_refresh_net_sales: 1400,
  line_count: 3}`, `{unposted_documents: 2, total_documents: 30}`) fails; the
  prompt's alias rule makes this rare.
- **Tolerance rule**: cases whose compared values are sums of line-level money
  (`SalesDocumentLine.NetAmount`: `core_public_008`, `edge_public_001`,
  `edge_public_002`, `edge_public_006`, `paraphrase_public_008`) set
  `tolerance: 0.01`. The fixtures hold sub-cent line amounts, so
  `SUM(ROUND(x, 2))` and `ROUND(SUM(x), 2)` legitimately differ by up to a cent
  (the generator keeps at most two half-cent lines in any group). Header and
  posting amounts are whole cents, so those cases keep exact 2-decimal
  equality; counts and quantities never get a tolerance.

Mode distribution across the committed cases:

| Dataset | scalar | rowset | ranked |
|---|---|---|---|
| `core-public` (9) | 3 | 1 | 5 |
| `paraphrase-public` (9) | 3 | 1 | 5 |
| `edge-cases-public` (17) | 5 | 3 | 9 |

## Oracle controls and kill rate

`datasets/controls/<dataset>.json` holds, per case id, **negative** controls
(plausible-but-wrong SQL the oracle must kill: fail to match on at least one
fixture) and **positive** controls (correct alternatives it must accept on every
fixture, which must also pass the production validator). Core-case controls
live in `core-public.json` (the edge suite reuses those cases by id);
paraphrases resolve by `intentId` when their gold SQL is the same; a
`gold_fingerprint` flags controls whose gold changed. On the edge suite:

- **Audit controls** (ids `m*`, `h*`, `a*`), ported from the audit's mutation
  workstream: 108 design mutants, 28 held-out mutants (`heldout: true`,
  written after the v2 fixture was frozen), and 32 of its 35 correct
  alternatives (dropped: the two containing SQL comments, which the validator
  rejects in any model output, and core_004's copy of the gold), plus 5 new
  positives for the alternative readings and alias forms.
- **Review controls** (ids `r*`, `rp*`, notes start with `review:`), added
  after the PR review: 44 design negatives for the families the review found
  surviving all three fixtures (MONTH() without YEAR() on every March case,
  SUM(DISTINCT …) on every summed measure, invented Customer/Product
  `IsActive` filters, hedged answers, a cancel filter on one side of a set
  difference, a NULL-keeping set difference, a ranking without ORDER BY, two
  data-dependent customer sets for the `edge_public_008` pivot) and 34 of its
  38 correct alternatives (not the two the scalar rule rejects, see below, nor
  the two that filter on the seed prompt's candidate IDs or codes, which the
  offline validator test cannot reproduce without a database). One of them (`core_public_004/rp4`, GROUP BY … HAVING
  `SUM(d.DocumentDate < …)` over line-joined headers) is flagged
  `validator_known_false_rejection`: the FAN_OUT guardrail rejects a boolean
  header aggregate that cannot fan out. `verify-dataset` reports it as a note,
  and a test fails once the guardrail accepts it, so the flag cannot go stale.

Measured with `npm run verify-dataset` on a fresh container
(`edge-cases-public`, which carries every control). "Alone" means the oracle
run with that single fixture:

| Controls | Seed only (old oracle) | Seed alone | v2 alone | v3 alone | All three fixtures |
|---|---|---|---|---|---|
| 108 audit design mutants killed | 50 (46.3%) | 51 (47.2%) | 107 (99.1%) | 98 (90.7%) | **108 (100%)** |
| 28 audit held-out mutants killed | 12 (42.9%) | 12 (42.9%) | 27 (96.4%) | 25 (89.3%) | **28 (100%)** |
| 44 review design negatives killed | — | 8 (18.2%) | 42 (95.5%) | 39 (88.6%) | **44 (100%)** |
| All 152 design negatives killed | — | 59 (38.8%) | 149 (98.0%) | 137 (90.1%) | **152 (100%)** |
| 71 positive controls accepted | — | — | — | — | **71/71 by the oracle; 70/71 by the validator + 1 flagged known false rejection** |

"Seed only (old oracle)" is the pre-change `evaluateQuestion` on the old seed
(the audit's number, reproduced). The new seed-only number loses the 5 kills
that came from the disallowed-column regex (now a warning) and gains 6: three
core_007 readings and two master-data mutants caught by the shared master rows,
and the swapped Jan/Feb pivot caught by name pinning. `verify-dataset` fails
below a design kill rate of `--min-kill-rate` (default 0.95, all non-held-out
negatives); the held-out rate is reported without a floor
(`--min-heldout-kill-rate`, default 0). A negative control counts as killed
only when it executes on every fixture and does not match: one that fails to
execute (a bad column, a timeout) is **invalid**, and one hit by an
infrastructure error (a dropped connection) is **unscored**. Both are
problems that fail `verify-dataset`, and both stay in the denominator as not
killed, so a broken control or a lost connection can only lower the reported
rate, never raise it.

**Read these as fitted numbers, not a generalization estimate.** The fixtures
were extended until the controls died: v2b after the audit's held-out mutants
were seen, v2c and the v3 changes after the review's survivors were seen. The
review wrote 50 new non-hedging wrong queries and 8 wrong hedges (two
readings, or a wrong gold-named column next to the right value) against the
previous fixtures, without looking at the controls:

| Review's adversarial set | Before (previous fixtures and comparator) | After |
|---|---|---|
| 50 wrong queries killed, all fixtures | 29 (58%) | 49 (98%) |
| … seed / v2 / v3 alone | 8 / 21 / 26 | 9 / 44 / 45 |
| 8 wrong hedges killed | 1 | 8 |
| 38 correct alternatives accepted | 34 | 36 |

Most of those queries are now controls, so the "after" column is fitted too.
The honest reading: one tiny seed catches under half of plausible-wrong SQL;
fixtures designed against known mistake families catch nearly all of those
families; a new family is caught only if some fixture happens to separate it.

### Known blind spots

Kinds of wrong SQL the oracle is known to let through (none is a control,
since none would be killed):

- **Contrived posting readings**: "only debit postings count as postings"
  (`NOT EXISTS (… AND p.DebitAmount > 0)` for `core_public_006`) passes,
  because every posted document has an AR debit.
- **Filters equivalent on this master data**: `ProductTags LIKE '%seltzer%'`
  alone for "sparkling water" (every sparkling SKU carries the tag), "active =
  `IsActive = 1` and a segment" (every customer has one), a LEFT JOIN from
  DocumentType with `HAVING COUNT(…) > 0`. Separating them would need more
  master rows, which every fixture (the seed included) would share.
- **Label-only swaps of unrelated names** in the gold's column positions (see
  column_order above).
- **Readings no fixture separates yet**: any new mistake family is caught only
  by chance; add a fixture row and a control when one is found.

And correct SQL it rejects (known false negatives): the scalar rule's extra
numeric column under an unrelated alias (above), and the validator's FAN_OUT
false rejection of `core_public_004/rp4`.

## Current baseline

The benchmark (`npm run benchmark`) runs each case through the **product loop
itself**: `evaluateQuestion` calls `runOptimizedQuestion`, the same function the
web app and the optimized CLI use, so master-data resolution, the prompt, the
retry message, the retry budget (`WEB_QUERY_MAX_RETRIES`, default 1 retry = 2
attempts) and the statement timeout (`QUERY_STATEMENT_TIMEOUT_MS`, default
8000 ms) are the product's, not a copy. The product loop runs on the primary
fixture; the final SQL is then scored on every fixture (`--fixtures` selects a
subset that must include `seed`). Each result records per-attempt data
(generated SQL, validation code and layer, execution outcome, usage/cost,
timings), the per-fixture verdicts, and the warnings; every product-loop event
is also forwarded, tagged with the case, to the run's trace file. Gold SQL runs
first, with its own timeout (`GOLD_STATEMENT_TIMEOUT_MS`, 30 s), so a broken or
slow gold costs no LLM call and is never reported as a model failure.

Known gap: a failed LLM attempt that was still billed (a truncated or refused
completion) counts in the case's `llm_usage` / `llm_cost` but has no usage in
its `attempts[i].llm`, because the product loop's `llm.failed` trace event does
not carry it; per-attempt sums can therefore be lower than the totals.

Report changes compared with the previous benchmark (for consumers of
`report.json` and the trace; no in-repo consumer reads the old fields):

- per case, `signal_check_result` is now `signal_warnings` and
  `disallowed_columns_used` is now `disallowed_column_warnings`; both are
  warnings (`warnings: ['low_signal_success' | 'disallowed_column_used']`),
  never statuses; new per-case `attempts`, `oracle` (matched gold variant,
  reason, per-fixture verdicts, the fixtures that killed it, column
  assignment) and `timings`;
- new status `infra_error` (an infrastructure failure in the product loop or
  while the oracle re-runs the prediction on another fixture);
- new top-level `oracle` (fixture statuses, retry budget, statement and gold
  timeouts) and `warningCounts`;
- the `case.completed` trace event no longer carries `expectedRowCount`,
  `actualRowCount`, `signalCheckResult` or `disallowedColumnsUsed`; per-fixture
  row counts are in its `perFixture`, and the warnings in `result.signal_checked`.

The committed datasets are intentionally small and cover a limited set of
intents — treat their numbers as **smoke signals, not a reliability claim**. No
fixed pass-rate is committed, on purpose: generation is non-deterministic, so a
single `accuracy: 1.0` is a lucky sample, not evidence. Measure reliability with
repeated runs and report the honest lower bound:

```bash
npm run benchmark -- --dataset core-public --repeat 10
```

In `--repeat` mode the report adds a `reliability` block with per-run min/mean/max
accuracy, the overall pass-rate, per-case pass rates, and a **Wilson 95% lower
bound** on the true pass-rate (`wilsonLowerBound`, z = 1.96, in
`scripts/evaluate.js`). The Wilson lower bound is the headline number: 6/6 on one
run has a lower bound near 0.6, not 1.0. Reliability mode is a measurement and
never fails the process on expected run-to-run variance. Grow `datasets/` with
execution-verified gold queries before making any reliability claim. Pass rates
measured before this oracle (one seed, alias-keyed signal checks) are not
comparable with the three-fixture numbers.

The few-shot examples in the prompt (`FEW_SHOT_EXAMPLES` in `src/constants.js`)
no longer contain any dataset question or gold SQL;
`test/few-shot-leakage.test.js` keeps it that way (no equal question, no equal
SQL, token Jaccard < 0.8 with every gold).

## Coverage limits

Known gaps, verified in code — do not read more into the suite than it tests:

- **Temporal**: normalization handles **month-name + year** only (no relative
  dates, quarters, or YTD).
- **Master data**: resolution is **product-only**; other entity types are not
  resolved before generation.
- **Empty results**: no committed case has a zero gold row count on any fixture.
  The pipeline *handles* a genuine zero-row answer (a dedicated empty-result
  insight card and an `empty_result_set` signal check), but the suite does not
  *target* empty-result robustness.
- **Accounting dates**: `core_public_005` / `core_public_009` filter postings by
  the sales document's `DocumentDate`; a posting-date reading
  (`AccountingPosting.PostingDate`) is plausible for ledger questions and now
  gives a different answer on v2/v3. It is not accepted as an alternative yet.
- **Guardrails**: the unqualified-identifier check only flags mixed-case unknown
  identifiers, and accepts an output alias used in WHERE (MariaDB rejects it at
  execution); joins between two foreign keys to the same table (e.g.
  `CustomerProductPrice.ProductId = SalesDocumentLine.ProductId`) are still
  rejected as JOIN_PATH (no dataset case needs one); FAN_OUT rejects a boolean
  header aggregate over line-joined headers (`core_public_004/rp4`).

## Running it

Run locally after starting MariaDB (`docker compose up -d mariadb`; the init
script creates the SELECT-only query user). Seed every fixture, then validate
every gold query and the oracle **without spending any LLM calls** (run this
after schema/data changes to separate dataset rot from model regressions):

```bash
npm run seed-fixtures                             # admin role; idempotent
npm run verify-dataset                            # all datasets, all fixtures
npm run verify-dataset -- --dataset edge-cases-public
npm run verify-dataset -- --dataset-file my.json --fixtures seed --skip-controls
npm run verify-dataset -- --write-pins            # rewrite expected_row_counts
npm run evaluate-retrieval -- --dataset edge-cases-public
```

The opt-in database tests re-seed the fixture databases and check the master
data is identical across them (read as the query user), that edited rows are
detected as drift and repaired, the verify logic, and the benchmark CLI end to
end against a local stand-in for the OpenAI API (no paid call). Like
`test/mariadb.integration.test.js` they run when `TEST_MARIADB_PORT` is set;
the seeding tests also need the admin password and FAIL with that message
(not a silent skip) when `TEST_MARIADB_ADMIN_PASSWORD` is missing. They write
`demo_retail*`, so point them at a throwaway server:

```bash
TEST_MARIADB_PORT=3306 TEST_MARIADB_PASSWORD=<DB_PASSWORD> \
TEST_MARIADB_ADMIN_PASSWORD=<root password> \
  node --test test/eval-fixtures.integration.test.js test/mariadb.integration.test.js
```
